Kan uses Supabase for authentication (Supabase Auth) and file storage (Supabase Storage). This is a **mandatory dependency** for all deployments, including self-hosted Docker Compose setups.

<Note type="warning">
  Starting with this version, a Supabase project is **required** to run Kan —
  even when self-hosting with Docker Compose. You can use either [Supabase
  Cloud](https://supabase.com) (free tier available) or [self-host Supabase](https://supabase.com/docs/guides/self-hosting/docker)
  on your own infrastructure.
</Note>

## Why Supabase is required

Kan previously used Better Auth for authentication and S3-compatible storage for file uploads. Both have been replaced by their Supabase equivalents:

- **Supabase Auth** handles user registration, login (email/password and OAuth), session management, magic links, and account deletion.
- **Supabase Storage** handles avatar uploads and card attachments via signed URLs.

This consolidation simplifies the stack and removes the need for separate S3 credentials and the Better Auth runtime. The PostgreSQL database connection (`POSTGRES_URL`) remains independent — you can still point it at any standard Postgres instance.

## Options for obtaining Supabase credentials

<Tabs>
  <Tab title="Supabase Cloud (recommended)">
    The simplest path. Create a free project at [supabase.com](https://supabase.com) and copy the credentials from the dashboard.

    **Pros**: zero infrastructure to manage for Auth and Storage, generous free tier.

    **Cons**: data lives on Supabase's infrastructure, subject to their terms.
  </Tab>
  <Tab title="Self-hosted Supabase (supabase/docker)">
    Run the full Supabase stack (Auth, Storage, PostgREST, etc.) on your own server using the official Docker Compose setup.

    **Pros**: full control over data and infrastructure, no external dependency.

    **Cons**: heavier installation (multiple containers), you manage upgrades and availability.

    See the [official self-hosting guide](https://supabase.com/docs/guides/self-hosting/docker) for setup instructions.
  </Tab>
</Tabs>

## Required environment variables

Kan needs three Supabase-specific variables to connect to Auth and Storage:

| Variable | Description |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | The URL of your Supabase project (e.g., `https://<project-ref>.supabase.co` for cloud, or your self-hosted Kong URL). |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | The public anonymous key. Used by the browser client for Auth operations scoped by Row Level Security. |
| `SUPABASE_SERVICE_ROLE_KEY` | The service role key (server-only). Used by backend code to bypass RLS for admin operations (e.g., deleting users, managing storage). **Never expose this in client-side code.** |

<Note type="warning">
  The `SUPABASE_SERVICE_ROLE_KEY` has full access to your Supabase project.
  Treat it like a database password — keep it out of version control and
  client-side bundles.
</Note>

## Setup steps

<Steps>
  <Step title="Create a Supabase project">
    **Cloud**: sign up at [supabase.com](https://supabase.com), create a new project, and wait for it to finish provisioning.

    **Self-hosted**: follow the [Supabase Docker guide](https://supabase.com/docs/guides/self-hosting/docker) to bring up the stack. Once running, you'll have a local URL (e.g., `http://localhost:8000`) and the keys printed in the setup output.
  </Step>

  <Step title="Get your credentials">
    In the Supabase dashboard, go to **Project Settings → API**:

    - **Project URL** → this is your `NEXT_PUBLIC_SUPABASE_URL`
    - **anon / public** key → this is your `NEXT_PUBLIC_SUPABASE_ANON_KEY`
    - **service_role / secret** key → this is your `SUPABASE_SERVICE_ROLE_KEY`

    For self-hosted Supabase, these values are set in your Supabase `.env` file and printed during initial setup.
  </Step>

  <Step title="Create storage buckets">
    Kan expects two storage buckets:

    - `avatars` — for user profile images
    - `attachments` — for card file attachments

    You can create them via the Supabase dashboard (**Storage → New bucket**) or using the Supabase CLI/API. Set both as **private** buckets (Kan uses signed URLs for access).
  </Step>

  <Step title="Configure OAuth providers (optional)">
    If you want social login (Google, GitHub, Discord, etc.), configure the providers in **Authentication → Providers** in the Supabase dashboard. Enter the client ID and secret from each provider's developer console.

    <Note>
      OAuth configuration is done entirely in the Supabase dashboard, not via
      environment variables in the application. The app's OAuth env vars (e.g.,
      `GOOGLE_CLIENT_ID`) only control which buttons appear in the UI.
    </Note>
  </Step>

  <Step title="Add the variables to your .env file">
    Add the three variables to your `.env` file used by Docker Compose:

    ```bash
    # Supabase (required for Auth and Storage)
    NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
    NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOiJI...
    SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJI...
    ```

    The `docker-compose.yml` already passes these to the `web` service alongside `BETTER_AUTH_SECRET` and `POSTGRES_URL`.
  </Step>

  <Step title="Start Kan">
    ```bash
    docker compose up -d
    ```

    Kan will use Supabase Auth for all authentication flows and Supabase Storage for file uploads. The PostgreSQL database (`POSTGRES_URL`) remains your own Postgres instance managed by Docker Compose.
  </Step>
</Steps>

## Session configuration

Supabase Auth manages session duration and refresh token behavior. To match Kan's defaults (30-day session, 48-hour refresh window), configure these in the Supabase dashboard under **Authentication → Settings**:

- **JWT expiry**: `2592000` seconds (30 days)
- **Refresh token reuse interval**: adjust based on your security requirements

## Troubleshooting

<AccordionGroup>
  <Accordion title="App starts but login/signup fails">
    - Verify `NEXT_PUBLIC_SUPABASE_URL` is reachable from the `web` container (use `docker exec` to test connectivity).
    - Check that `NEXT_PUBLIC_SUPABASE_ANON_KEY` matches the anon key shown in your Supabase dashboard.
    - Review the app logs for descriptive error messages: `docker compose logs web`.
  </Accordion>

  <Accordion title="File uploads fail (avatars, attachments)">
    - Confirm the `avatars` and `attachments` buckets exist in Supabase Storage.
    - Verify `SUPABASE_SERVICE_ROLE_KEY` is correct — the service role key is needed to generate signed upload URLs.
    - Check the health endpoint (`/api/v1/health`) — it reports `not_configured` or `error` for storage issues.
  </Accordion>

  <Accordion title="Self-hosted Supabase: connection refused">
    - Ensure the Supabase Kong gateway is accessible from the Kan Docker network.
    - If running both Kan and Supabase on the same host, use Docker network aliases or the host's IP rather than `localhost`.
    - Check that ports are not blocked by a firewall.
  </Accordion>

  <Accordion title="OAuth providers not showing up">
    - Provider buttons only appear when the corresponding env vars (e.g., `GOOGLE_CLIENT_ID`) are set to a non-empty value.
    - The actual OAuth flow uses credentials from the Supabase dashboard — make sure they're configured there too.
    - Kick, Dropbox, VK, Reddit, and Roblox are **not supported** by Supabase Auth.
  </Accordion>
</AccordionGroup>
