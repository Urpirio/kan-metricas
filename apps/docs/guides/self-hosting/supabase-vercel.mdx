This guide walks through deploying `apps/web` to Vercel while using Supabase Postgres as the database. It covers where to find each Supabase connection string, which one to use for runtime versus migrations, how to point Vercel at the right directory in the monorepo, and how to run your migrations before the first deploy.

<Note>
  This is an alternative to the Docker Compose setup covered in the
  [Introduction](/guides/self-hosting/introduction). The Docker path still works
  and is unchanged — this guide adds a managed Supabase + Vercel flow on top of
  it.
</Note>

## Prerequisites

- A Supabase project ([supabase.com](https://supabase.com))
- A Vercel account connected to your Git provider
- A long random string for <code>BETTER_AUTH_SECRET</code> (32+ chars)

## Understanding the two connection strings

Supabase exposes two ways to connect to your database, and Kan uses **both** for different purposes:

<CardGroup cols={2}>
  <Card title="Direct connection" icon="plug" horizontal>
    Host <code>db.&lt;project&gt;.supabase.co</code>, port <code>5432</code>. A
    dedicated session per connection. Used for **migrations**.
  </Card>
  <Card title="Pooled connection" icon="layer-group" horizontal>
    Host <code>aws-0-&lt;region&gt;.pooler.supabase.com</code>, port{" "}
    <code>6543</code> (transaction mode) via Supavisor. Used at **runtime** on
    Vercel.
  </Card>
</CardGroup>

<Note type="warning">
  Migrations must run against the **direct** connection. Supavisor’s transaction
  mode (port 6543) does not support the session-level statements and prepared
  statements that migration tools rely on, so running <code>db:migrate</code>{" "}
  through the pooler will fail or behave unpredictably. The pooled connection is
  meant for short-lived serverless queries, where sharing a small pool of real
  connections across many function invocations avoids exhausting Postgres’
  connection limit.
</Note>

## Setup

<Steps>
  <Step title="Get both connection strings from Supabase">
    In the Supabase dashboard, go to **Project Settings → Database**.

    - Under **Connection string**, copy the **Direct connection** (port `5432`, host `db.<project>.supabase.co`). This is your migration connection.
    - Under **Connection pooling**, copy the **Transaction** pooler string (Supavisor, host `aws-0-<region>.pooler.supabase.com`, port `6543`). This is your runtime connection.

    Replace the `[YOUR-PASSWORD]` placeholder in each string with your database password.

    <Tip>
      The pooled string includes your project ref in the username (for example
      <code>postgres.&lt;project-ref&gt;</code>). Copy it exactly as shown in the
      dashboard rather than editing the direct string by hand.
    </Tip>

  </Step>

  <Step title="Configure the environment variables">
    Kan reads two Postgres variables:

    ```bash
    # Runtime (Vercel serverless functions) → pooled / Supavisor transaction mode
    POSTGRES_URL=postgresql://postgres.<project-ref>:[YOUR-PASSWORD]@aws-0-<region>.pooler.supabase.com:6543/postgres

    # Migrations only → direct connection
    POSTGRES_URL_NON_POOLING=postgresql://postgres:[YOUR-PASSWORD]@db.<project>.supabase.co:5432/postgres
    ```

    - <code>POSTGRES_URL</code> — the **pooled** connection. The app uses this at runtime because serverless functions scale to many concurrent instances, and the pooler keeps the number of real Postgres connections bounded.
    - <code>POSTGRES_URL_NON_POOLING</code> — the **direct** connection. The migrator uses this because migrations need session-level statements that the pooler’s transaction mode doesn’t support. If this variable is not set, the migrator falls back to <code>POSTGRES_URL</code>.

    Set both in your Vercel project (**Project Settings → Environment Variables**), along with the rest of Kan’s required variables (<code>NEXT_PUBLIC_BASE_URL</code>, <code>BETTER_AUTH_SECRET</code>, …). See the README’s Environment Variables section for the full list.

    <Note>
      SSL is handled automatically: Kan enables SSL for managed hosts like
      Supabase unless the connection string already specifies an{" "}
      <code>sslmode</code> parameter, so you don’t need to add one manually.
    </Note>

  </Step>

  <Step title="Set the Vercel Root Directory to apps/web">
    Kan is a pnpm/Turborepo monorepo, so tell Vercel which package to deploy.

    In the Vercel dashboard, open **Project Settings → Root Directory** and set it to:

    ```
    apps/web
    ```

    Vercel auto-detects the Turborepo build. The repo ships an `apps/web/vercel.json` that declares:

    - Install command: `pnpm install --frozen-lockfile`
    - Build command: `turbo run build --filter=@kan/web`

    <Note type="warning">
      Do **not** set <code>NEXT_PUBLIC_USE_STANDALONE_OUTPUT</code> on Vercel.
      That flag is only for the Docker build (`apps/web/Dockerfile`), which needs
      Next.js standalone output. On Vercel, let it use its own Next.js
      packaging — setting the flag will break the deploy.
    </Note>

  </Step>

  <Step title="Run migrations before the first deploy">
    Unlike the Docker Compose setup, Vercel does **not** run the migrator container. You must apply migrations yourself against the **direct** connection before the first deploy (and after any future schema change).

    From the repo root, with `POSTGRES_URL_NON_POOLING` set to your direct connection string:

    ```bash
    pnpm db:migrate
    ```

    This runs Drizzle migrations through the direct connection (port 5432), which supports the statements the migrator needs.

    <Tip>
      You can export the variable inline for a one-off run:

      ```bash
      POSTGRES_URL_NON_POOLING="postgresql://postgres:[YOUR-PASSWORD]@db.<project>.supabase.co:5432/postgres" pnpm db:migrate
      ```
    </Tip>

  </Step>

  <Step title="Deploy">
    Push to your production branch (or trigger a deploy from the Vercel dashboard). Vercel installs dependencies, builds `@kan/web` via Turborepo, and serves the app.

    Because migrations already ran in the previous step, the deployed app connects to an up-to-date schema through the pooled connection.

  </Step>
</Steps>

## Configuring OAuth providers (Social Login)

OAuth provider configuration (client id/secret for Google, GitHub, Discord, etc.) is done entirely in the **Supabase dashboard**, not via environment variables in the application.

<Steps>
  <Step title="Enable providers in the Supabase dashboard">
    Go to **Authentication → Providers** in your Supabase project dashboard. Enable the providers you want and enter the corresponding client ID and client secret obtained from each provider's developer console.
  </Step>

  <Step title="Set callback URLs">
    Each provider requires a redirect/callback URL. Supabase provides the correct callback URL in the provider configuration panel (typically `https://<project-ref>.supabase.co/auth/v1/callback`). Enter this URL in the provider's developer console (e.g., Google Cloud Console, GitHub OAuth App settings).
  </Step>

  <Step title="(Optional) Show provider buttons in the Kan UI">
    To control which social login buttons appear in the Kan login/signup UI, set the corresponding environment variables with any non-empty value:

    ```bash
    GOOGLE_CLIENT_ID=configured
    GOOGLE_CLIENT_SECRET=configured
    GITHUB_CLIENT_ID=configured
    GITHUB_CLIENT_SECRET=configured
    ```

    These variables are read only to determine which buttons to display. The actual OAuth handshake uses the credentials stored in the Supabase dashboard.
  </Step>
</Steps>

<Note type="warning">
  The following providers are **not supported** by Supabase Auth and will never be shown in the UI, even if their environment variables are set: **Kick**, **Dropbox**, **VK**, **Reddit**, **Roblox**. The generic OIDC provider has also been removed.
</Note>
